Eden Playground · MVP1

MVP1 Feature List

Audience: Product, Co-founders Last reviewed: April 2026 Phase: Pre-build · Feature definition

Every feature we need to build for MVP1 — and nothing we don't. This document is the line between what goes into the first real user cohort and what waits for later. If a feature isn't here, it doesn't get built yet.

✓ MVP1 definition: A real user (university student) can receive an invitation, complete Gaia Invitation, play through one content World, receive a debrief, earn a token, and return to continue — while generating valid, research-quality experiment data throughout. That is the whole scope. Everything else is Phase 2.

01 What's in and what's out

In MVP1
  • Invite / entry flow
  • Consent — woven into narrative
  • Return-key identity (pseudonymous)
  • Gaia Invitation World (full)
  • 1 content World — Deal or Urgency (TBD)
  • Experiment arm assignment (A/B)
  • Token earn on World completion
  • Debrief experience
  • Journey pause and resume
  • Wellbeing / opt-out checkpoint
  • Basic event logging for research
  • Invite code generation (minimal)
Not in MVP1
  • Shield of Eden (needs all Worlds)
  • Ambassador / sharing flow
  • Worlds 3–6 (Social, Gamification, Advertising, …)
  • Second narrative theme (Sci-fi)
  • Research dashboard
  • Admin dashboard
  • Adaptive content (LOLA algorithm)
  • Automated analysis / batch jobs
  • Social login or third-party auth
  • Multilingual support (pending decision)
  • Public landing page / SEO
  • Notification or email system

02 Identity and access

How a user gets in and how they get back. No email, no account. One downloadable key.

Feature What it does Why it's in MVP1 Status
Invite code entry
User arrives with an invite code (from a university channel, email link, or QR). Entering it starts the journey. No account creation — just the code as the gate.
Controls who enters in the first student cohort. Keeps sample quality high. Required before any consent or data collection begins.
to design
Return key generation
On first entry, user is given a unique pseudonymous key — presented as their "traveller's token." They are prompted to download or copy it before proceeding. This key is their only identity on the platform.
Core privacy-by-design principle. No email or PII. The key ties all their events, progress, and experiment assignment together without identifying them.
to design
Return key re-entry
Returning user pastes or types their key to resume their journey exactly where they left off — same World, same arm, same progress.
The multi-World journey requires multiple sessions. Without reliable return, every user is effectively a new user after session 1. Journey completion is impossible without this.
to design
Key loss recovery
If a user loses their key, they have one recovery option — to be determined. Options: optional email backup (consent-gated), manual admin recovery, or no recovery (key-loss = restart).
Key-loss is the highest structural risk to journey completion. Needs a defined policy before build, even if the policy is "no recovery" — that has product and research implications.
open — needs decision

03 Consent and onboarding

Informed consent before any data is saved — woven into the narrative, not a separate screen.

Feature What it does Why it's in MVP1 Status
Narrative consent gate
Before any data is collected, the user is told — in Gaia's voice, in the narrative register — that they will encounter real persuasive design techniques, that their choices may be observed, and that they are pseudonymous. They actively continue to proceed. This is the consent moment.
Non-negotiable ethics requirement. Also sets the emotional register correctly: users arrive knowing this is a deliberate experience, which makes the debrief land harder. Cannot be skipped or abbreviated.
to design
Consent record
The moment of consent is logged against the user's key — timestamp, version of the consent text shown, and explicit confirmation action. This record is immutable.
Required for research validity and ethics committee compliance. Without a logged record of consent, no data collected in that session can be used in research outputs.
confirmed in
Opt-out at any point
A persistent, low-friction way to stop participating and request data deletion — available throughout the entire experience. Not hidden. Not buried. Mentioned in the consent flow so users know it exists before they start.
Ethics requirement. Informed consent is only meaningful if withdrawal is genuinely available and easy. Must be accessible in every World, not just at the end.
confirmed in

04 Gaia Invitation World

The entry narrative. Sets the mission, establishes Gaia's voice, and earns the user's investment before they reach the first technique World.

Feature What it does Why it's in MVP1 Status
Gaia's invitation scene
The opening experience: Gaia addresses the user directly. Establishes who Gaia is, what the manipulation crisis means, and why the user has been chosen. Sets emotional stakes. This is not a tutorial — it is a story that happens to explain the journey.
First impression. The narrative framing either hooks the user here or loses them. No content World can work without this existing first.
to design
Journey map reveal
After the invitation, the user sees the full journey ahead — the Worlds they will travel through, rendered as destinations on a map, a star chart, or equivalent. Worlds beyond MVP1 can be shown as locked/distant. The user sees where they are going.
Creates commitment and anticipation. Users who see the full arc are more likely to return after World 1. The map is also the navigation state — it shows progress at every return.
to design
First token moment
Completing Gaia Invitation earns the first token — the "Orb of Beginning" or equivalent. This is the moment the token mechanic becomes real and tangible for the user before they reach any technique content.
Establishes the reward loop before the research content begins. If the first token feels good, users know what they are working toward in World 1.
to design
Experiment arm assignment
At the point of World entry, the user is silently assigned to an experiment arm. The assignment is logged and sticky — they see the same version on every return. For MVP1, this is a simple A/B split (e.g., two versions of the invitation narrative or consent phrasing).
Research integrity. Without logged, sticky assignment, the experiment is invalid. Must happen at first entry, before any content is shown.
confirmed in

05 World 1 — Content World (Deal or Urgency)

The first technique World. Users encounter real manipulative patterns embedded in a narrative mission. They do not know the debrief is coming.

◈ Which World goes first is still open. Deal World (pricing psychology) or Urgency World (artificial scarcity and countdowns). The features below apply to whichever is chosen — the structure is identical. The content is different. See open questions.
Feature What it does Why it's in MVP1 Status
Narrative mission frame
The World presents a narrative context — a market stall, a festival gate, a timed auction — within which the manipulative techniques are embedded. The user has a mission to complete. The techniques are the obstacles and temptations, not the stated subject.
The techniques must be experienced, not described. The narrative frame is what makes the experience real rather than a simulation. Without it, the debrief has nothing to reveal.
to design
Live technique embedding
Real manipulative techniques — at real-world intensity, not amplified — are woven into the World's choices and environment. Users make decisions. The techniques act on them. Their choices are logged as behavioural events.
The core product mechanism. This is the thing no other awareness platform does. Users feel the technique before they understand it.
to design
Experiment arm variants
The World has at least two versions (A and B), differing in one specific way: a different technique version, a different intervention, or a different framing. Users see only their assigned version. Both versions are complete experiences.
Research validity. One version is not science. Two versions with random assignment and logged outcomes is the minimum for a publishable finding.
to design
Mission completion condition
A clear, achievable success state for the World — reaching a destination, completing a transaction, making the right call. Completion triggers the debrief and token. Failure has a defined outcome too (retry, or proceed to debrief without token).
Without a completion condition, there is no token, no debrief trigger, and no journey progression. The research data also needs a defined success event to analyse against.
to design
Behavioural event logging
Every meaningful user action within the World is logged: decisions made, time spent, paths taken, choices accepted or rejected. Logged against the user's key and experiment arm. Append-only, no PII.
This is the research data. Without it, the experiment produces no output. Must be running from the first user's first session.
confirmed in
Wellbeing checkpoint
At natural pause points within the World — and always available via a low-friction persistent control — users can check in on how they are feeling and exit cleanly if needed. This is not an interruption; it is a door that is always unlocked.
Ethics guardrail. Technique intensity mirrors real-world commercial platforms, but some users may still find it activating. The checkpoint must exist before any technique content runs.
confirmed in

06 The debrief

The moment the World reveals what just happened. This is the core awareness mechanism — the reason the whole platform exists.

Feature What it does Why it's in MVP1 Status
The reveal moment
After the mission resolves, the World pauses and — in Gaia's voice or the World's narrative register — names what just happened. The technique is identified. The mechanism is explained. A real-world parallel is given. This is storytelling, not a screen of facts.
Without the debrief, the experience is manipulation without awareness. The debrief is the product's entire value proposition. It cannot be a summary paragraph — it must land emotionally.
to design
The portable mental model
After the reveal, the user receives one concise, memorable frame for the technique — something they can carry with them and apply in daily life. A question to ask, a phrase to remember, a pattern to look for. Designed for retention, not comprehensiveness.
The product's impact extends beyond the platform only if something transferable is given. "You were anchored" is awareness. "Next time you see a crossed-out price, ask: what was that price anchored to?" is a tool.
to design
Debrief comprehension check
One or two optional self-report questions after the debrief: did the user understand what technique they encountered, did the reveal feel surprising, how are they feeling. Low friction. Not a test. Labelled as voluntary.
Research guardrail and quality signal. If comprehension scores are low, the debrief design is failing. This is the most direct measurement of whether the awareness mechanism works.
confirmed in
Token award ceremony
After the debrief, the token is formally awarded. In the mythic theme: an orb materialises and joins the user's collection. The name of the token reflects what was learned (Orb of Clarity, Orb of Patience, etc.). Brief, satisfying, meaningful.
Closes the emotional arc of the World. The token represents understanding earned — not just time spent. It must feel like it means something, not like a pop-up badge.
to design

07 Journey state and return

How the journey persists between sessions and how users navigate back into it.

Feature What it does Why it's in MVP1 Status
Progress persistence
All user progress — Worlds completed, tokens earned, experiment assignment, event history — is tied to the return key and persists indefinitely. Returning with the key resumes exactly where the user left off.
The journey is multi-session by design. Without persistence, every return is a cold start and journey completion is structurally impossible. This is table stakes, not a feature.
confirmed in
Journey home / map state
On returning, the user lands on a journey view — a map or equivalent — that shows what they have completed, what token(s) they have earned, and what is next. Their current position in the journey is always visible.
Orientation on return. Without this, users returning after days ask "where was I?" and the answer is not obvious. The map is the product's navigation and motivation state combined.

08 Research and operational basics

The minimum infrastructure to run a valid experiment and invite the first cohort. Deliberately thin — we add tooling only after it is proven necessary.

Feature What it does Why it's in MVP1 Status
Event log
Append-only log of every meaningful user event — consent given, World entered, choices made, debrief reached, token earned, session ended. Tagged with key (pseudonymous), timestamp, World, and experiment arm. The raw research data.
Without this nothing can be analysed. Must be live from the first user's first action. No event log = no research = no product.
confirmed in
Invite code system
Ability to generate a batch of single-use or limited-use invite codes, share them with the university recruitment coordinator, and track which codes have been used. Manual or very minimal UI — this does not need to be a dashboard.
Controls who enters MVP1. Without this, the first cohort is ungated and sample composition is unknown. Must exist before recruitment begins.
to design
Data export
Ability to export the event log and self-report responses for offline analysis. A file download is sufficient for MVP1. No dashboard, no visualisations, no automated analysis.
The researcher needs to get at the data after the first cohort runs. If there is no export, Phase 1 produces no research output. Manual export is fine — it just needs to exist.
confirmed in

09 Explicitly out of MVP1 scope — and why

These are features that have been discussed, are on the product vision, and will be built — but not in MVP1. Listing them explicitly prevents them from creeping into the first build.

FeatureWhy it waitsWhen it becomes relevant
Shield of Eden + ambassador flow Requires all Worlds to be complete. Cannot exist until the full journey exists. Building the ceremony before the journey is finished is pure waste. After all Worlds are built and the journey is completable end-to-end.
Second narrative theme (Sci-fi) Theme is a research variable — you need Theme 1 working and producing data before you add Theme 2 as a comparison arm. Adding two themes in MVP1 doubles the design work for zero additional research value at this stage. After Theme 1 produces its first complete experiment result.
Adaptive content (LOLA algorithm) Adaptive optimisation requires a baseline of behavioural data to adapt against. Running it in MVP1 with 50 users produces noise, not signal. Human review requirements also mean it needs a content review pipeline first. After Phase 1 produces enough data to train against meaningfully — likely 500+ sessions minimum.
Research metrics dashboard Manual export is sufficient for the first cohort and the first analysis. A dashboard is operational convenience — it is not what makes the research valid. Build it when the manual process is too slow, not before. When cohort size makes manual export unworkable — probably Phase 2.
Admin dashboard Invite code generation and experiment configuration can be handled manually or through simple scripts at MVP1 scale. A dashboard UI is overhead that delays the actual product. When operational complexity makes manual management a bottleneck.
Public landing page / open access MVP1 is invite-only for a controlled student cohort. A public page invites uncontrolled traffic before the experiment is ready for it. Open access is Phase 2. When moving from student cohort to general public — Phase 2 launch.
Multilingual support Pending a decision on whether the MVP1 student cohort requires multiple languages. If English-only works for the first cohort, localisation waits. If not, it must come in — but it needs to be decided now, not discovered mid-build. Pending open question 5 below.

10 Open questions blocking feature decisions

These questions are blocking specific feature design choices. They need answers before those features can be specced or built.

Question 1 — Which World goes first
Deal World or Urgency World — and why, specifically for a student cohort that already knows these techniques academically?
The narrative design, technique embedding, debrief writing, and experiment arms are completely different for each World. This is the decision that unlocks all of Section 05. It cannot be deferred.

Question 2 — Key loss recovery policy
What happens when a student loses their return key? Three options: (a) optional institutional email backup at consent, gated by explicit opt-in; (b) manual admin recovery via the university coordinator; (c) no recovery — key loss means starting over as a new user. Which is it?
Option (a) solves the problem most elegantly but adds a data field. Option (b) adds an operational burden. Option (c) is clean but risks making journey completion impossible for students who lose their key between sessions — which students commonly do. The decision changes the identity feature design in Section 02.
Answer here…
Question 3 — What the experiment arms test in MVP1
For each World (Gaia Invitation and the content World), what are the two things being compared in the A/B split? Different narrative tones? Different intervention timings? Different technique intensities? This needs to be defined as a research hypothesis before the World can be designed.
Without defined arms, there is no experiment — just a product. The arms must be defined by the research question, not retrofitted after the World is built. Each arm is a complete version of the World; both must be designed together.
Answer here…
Question 4 — The debrief format
What does the reveal moment look and feel like? Is it Gaia speaking? A visual transformation of the World? A character stepping out of the narrative to explain? Text-only or visual? Does it include audio?
The debrief is the most important moment in the entire product. Its format determines the emotional impact of the awareness mechanism. This needs a creative decision — not a spec — before any design work begins.

Question 5 — Language scope for the student cohort
Is the MVP1 student cohort English-speaking, or does it include French-speaking or other students who would need a non-English experience? ESSEC has an international student body.
If English-only is sufficient for Phase 1, this is not in scope and waits for Phase 2. If the first cohort includes non-English speakers, multilingual support is an MVP1 requirement — and it changes the scope significantly. Needs a decision now.
