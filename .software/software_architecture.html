Eden Playground · Engineering

Software Architecture

Audience: Engineering, Co-founders Last reviewed: April 2026 Status: Pre-build · MVP1 scope

The implementation-level architecture for Eden Playground MVP1. Technology choices, data schema, API surface, world bundle format, deployment topology, and the open decisions that still block specific implementation choices. Read the product strategy and MVP1 feature list first.

✓ Scope boundary: This document covers MVP1 only — 50 university students, Gaia Invitation + one content World, A/B experiment, basic event log, invite codes, and data export. Everything marked Phase 2 (LOLA adaptive algorithm, research dashboard UI, admin UI, ambassador flow) is noted but not specified here.

01 Technology choices

One constraint drives all choices: a two-person team must be able to build, run, and debug this without a dedicated DevOps function. Everything below optimises for operability at small scale. When scale demands a change, the change is made then — not speculatively now.

Platform API
Python · FastAPI
Same language as batch analysis. Strong typing with Pydantic. Auto-generates OpenAPI docs. Async-ready.
Database
PostgreSQL 16
Single operational database. JSONB for event metadata. Supabase for hosted managed Postgres on free/pro tier.
World bundles
React · Vite
Each World is a small React app built with Vite. Versioned by path. Build output is static HTML/JS deployed to Vercel CDN.
API hosting
Railway
Docker-based. Simple env var config. Free tier covers MVP1 traffic. One-command deploys.
Batch analysis
Python · Pandas · Statsmodels
Jupyter notebooks for exploratory work. Scripts for scheduled runs. No separate compute platform needed at MVP1 scale.
Player shell
React + Tailwind CSS
Vite build. Component-driven UI for journey map, consent screen, return-key entry, and token ceremony. Tailwind for rapid styling without a design system overhead.
Dashboards (Phase 2)
Jinja2 templates
Server-rendered HTML from FastAPI. No separate frontend build. Admin and research metrics served from the same app on protected routes.
✓ Decision made: The player-facing shell uses React + Tailwind CSS, built with Vite. This gives a proper component model for the journey map, consent flow, return-key entry, and token ceremony without the overhead of a full design system. The build output is static HTML/JS deployed to Vercel — no server rendering required. See Section 11.

06 Experiment assignment flow

Assignment is deterministic and sticky. A session's arm is chosen at creation, written to experiment_assignments, and never changes. The World manifest endpoint reads the stored assignment — it never re-randomises.

flowchart LR A([Session created]) --> B["SHA-256\nsession_key + experiment_id\n→ float 0.0 to 1.0"] B --> C{"Walk weighted arms\ncumulative sum"} C -->|"val less than 0.5"| D["Assign: Arm A\nwrite to DB"] C -->|"val ≥ 0.5"| E["Assign: Arm B\nwrite to DB"] D --> F["Serve arm_A bundle\nvia /manifest"] E --> G["Serve arm_B bundle\nvia /manifest"] F --> H([Sticky forever\nnever re-randomised]) G --> H
# services/assignment.py
import hashlib

def assign_arm(session_key: str, experiment_id: str, arms: list) -> str:
    # Deterministic: same key + experiment always → same arm
    # Hash the key+experiment to a float in [0, 1)
    h = hashlib.sha256(f"{session_key}:{experiment_id}".encode()).digest()
    val = int.from_bytes(h[:4], "big") / 0xFFFFFFFF
    # Walk weighted arms until val falls in range
    cumulative = 0.0
    for arm in arms:
        cumulative += arm["traffic_weight"]
        if val < cumulative:
            return arm["arm_id"]
    return arms[-1]["arm_id"]  # fallback to last arm
→ The hash-based approach means if a user somehow loses their key and starts over with a new key, they get a fresh random arm — not the same arm. This is the correct behaviour for research integrity. It is also why key loss matters: you lose the ability to link their new session to their prior data.

07 World bundle format

A World is a versioned React app built with Vite. Each arm of an experiment lives in its own folder under /worlds. The build output is static HTML/JS deployed to Vercel. The Platform API's manifest endpoint tells the player shell which arm folder to load. The World does not know which arm it is — it just runs.

10 Return key format

The return key is the user's only persistent identity. It must be easy to write down (students may lose a downloaded file), hard to guess, and unique. A wordlist-based key balances memorability and entropy.

# services/key_gen.py
# Format: [adjective]-[noun]-[4-digit-hex]
# Example: silver-compass-3f7a
# Entropy: ~800 adjectives × ~1000 nouns × 65536 = ~52 billion combinations
# Sufficient for MVP1; upgrade to longer format if cohort exceeds 100K

import secrets

def generate_return_key() -> str:
    adj = secrets.choice(ADJECTIVES)
    noun = secrets.choice(NOUNS)
    suffix = secrets.token_hex(2)      # 4 hex chars
    return f"{adj}-{noun}-{suffix}"
→ Present the key to users as: "Your Traveller's Token is silver-compass-3f7a. Write it down or save it — this is the only way to return to your journey." The mythic framing ("Traveller's Token") makes storing it feel meaningful, not like a chore.

13 GitHub repository strategy

One repository. Not three. At two people and MVP1 scale, a monorepo eliminates the overhead of cross-repo PRs for changes that touch the API and the shell simultaneously — which is almost every meaningful change at this stage. Split when there is a concrete reason to split, not before.

✓ Decision: monorepo. Repository name: eden-playground. All source code, migrations, world bundles, analysis scripts, and internal docs in one place. Railway and Vercel both support per-subdirectory deploys from a monorepo natively.
