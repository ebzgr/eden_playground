Tech Stack

This page states the requirements that shaped v1, then the architecture chosen to satisfy them. Product and research detail is in the Conceptual Layer, Worlds, and Research Methodology. Jump to Requirements or Architecture principles. Concrete language and framework choices live under Technologies once decided.

Requirements

The following are constraints and goals the system must support. They are the reason for the deployables and boundaries described later—not the other way around.

Product and experience

  • Journey across Worlds: Users need a single, coherent narrative arc with progress, tokens, and gating between Worlds (see Worlds).
  • Versioned experiences: Worlds and narrative themes vary by version; the client must load the correct HTML/JS bundles for the assigned experiment arm.
  • Static world delivery: Worlds are composed of static assets; the platform must resolve which versioned paths to serve without requiring a heavy “builder” runtime.

Research and experimentation

  • Randomised assignment: Users must be assigned to arms/versions in a way that supports causal inference (Research Methodology).
  • Rich telemetry: Append-only capture of contextual, behavioural, and self-report events for analysis and guardrails.
  • Offline / batch analysis: Statistical workflows (A/B, heterogeneity, optional adaptive proposals) must run without blocking the live user path.
  • Reproducibility: Experiment definitions and content versions must be traceable from metrics and reports.

Privacy, ethics, and access

  • No email-first accounts: Pseudonymous continuity via a return key; minimise PII (Ethics & Data Protection).
  • Invite-only (v1): Access control for who can enter the playground at all.
  • Human review: Sensitive or adaptive changes to what users see must be governable (queues, approvals), not only code deploys.

Operations and scale (v1)

  • Low traffic, small team: Prefer simplicity and operability over premature scale-out; avoid many microservices until there is clear pain.
  • Observable research: Researchers and operators need to see experiment health and outcomes without a separate data engineering org at the start.

From requirements to design

Those needs map directly to: one authoritative backend (auth, progress, assignment, ingest), static hosting for world bundles, batch analysis for stats and aggregates, and internal dashboards backed by the same API with strong role separation—not a large fleet of independent services on day one.

Requirement area Primary architectural response
Journey, versioning, static Worlds Platform API (progress, assignment, manifest) + static asset hosts for versioned bundles.
Experiments, telemetry, reproducibility Experiment config and append-only event ingest in the Platform API + DB; batch Python jobs for analysis and aggregates.
Privacy, return keys, invite-only Identity and session semantics in the Platform API; admin dashboard for invites and governance.
Research and operator visibility Research metrics dashboard and admin UI as frontends on internal JSON routes, not separate metric backends at v1.
Simplicity at modest scale One backend deployable with clear modules; defer extra microservices until needed.

Architecture principles (v1)

The architecture below implements the requirements in the previous section. In short: prefer few running services over premature microservices. Worlds ship as versioned static bundles (HTML, JS, assets); a single Platform API handles auth, progress, experiments, telemetry, and internal JSON endpoints for dashboards. Analysis runs as batch jobs (Python) over the operational database or exports.

Deployables

Deployable Role
Platform API (single backend) Return-key / session auth; journey and progress; experiment assignment; event ingest; world manifest and version resolution; JSON APIs for research metrics and admin (separate route groups, role-based auth).
Static asset hosts Versioned world bundles and, if applicable, the public shell app separate from internal dashboards.
Operational database Sessions, progress, assignments, raw events, experiment definitions, admin configuration.
Batch jobs (Python) Scheduled analysis, aggregates for dashboards, exports; optional adaptive proposals as reviewable artefacts (not auto-applied without human review).
Research metrics dashboard (web UI) Per-experiment views: enrolment, arms, KPIs, guardrails, funnel and behaviour summaries; reads aggregates and experiment metadata via the Platform API (or read replicas / materialised views).
Admin dashboard (web UI) Invite codes; experiment create/update and status; content version pointers; feature flags; human-review queues; support actions that respect pseudonymity (see Ethics & Data Protection).

Dashboards

Dashboards are not separate backend services. Ship two UI surfaces (or one app with two authenticated areas): research metrics and admin. Both are static or server-rendered frontends that call the Platform API on internal routes (for example /api/internal/metrics/…, /api/admin/…) with role-based authentication (researcher vs operator). Splitting admin APIs into another deployable is optional later for compliance or blast-radius, not required at the start.

Platform API modules

Logical modules live inside the single backend until a split is justified by scale or policy:

  • Identity and return-key validation
  • Journey and progress (authoritative cross-world state)
  • Experiment configuration and assignment
  • Telemetry ingest (append-only)
  • Experience resolver (world id to static base URL or manifest)
  • Internal read models for dashboard queries (SQL views or thin handlers)

Data flow

Production path: browser to Platform API to database; events appended immutably.

Analytics path: database to batch Python jobs to aggregates, snapshot tables, or files; dashboards read aggregated data.

Avoid bidirectional sync between separate “research” and “production” data stores; v1 may use one database with clear schemas plus batch exports for heavier analysis.

Research dashboard ──► Platform API ──┐
Admin dashboard ──► Platform API ─────┤
                                                              ▼
Player app ──► Static world files
DB ──► Python batch jobs ──► DB / files (aggregates)

Deferred for later

  • Dedicated world-builder microservice (authoring stays repo, CI, static deploy, manifest).
  • Dedicated collaboration service (team tools; real-time multi-user worlds only if product requires).
  • Standalone metrics platform product (dashboards plus aggregates plus Python jobs until scale demands more).
  • Optional LLM / adaptive loop as a separate concern; when introduced, proposals pass human review before promotion to experiment config (see Brainstorming Board and research methodology).
